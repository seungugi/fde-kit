# 업무 담당자 AI와 대화할 프롬프트

README·데이터를 먼저 확인한 뒤, 아직 남은 운영 맥락의 공백 중 현재 답할 수 있는 중요 질문을 골라 한 번에 모아 보낸다. 질문마다 번호를 붙이고 앞선 답변에 의존하는 질문만 후속으로 남긴다. S1부터 전부 실행하는 순서표가 아니다. 상대에게 주어진 업무 역할과 정보를 존중하며, 특정 요일·수요량을 답으로 유도하지 않는다. 담당자의 답을 Codex에 전달할 때 질문 ID·출처와 관련 구현 명세 ID도 함께 옮긴다. 현장 사실은 담당자에게 확인하고 구현 방식은 참가자가 선택한다. 담당자 설명을 측정값이나 기능 추가 승인으로 취급하지 않는다.

대회에서 참가자가 메신저를 직접 조작해야 하면 아래 질문을 직접 전달한다. 키트가 화면을 자동 조작하거나 메시지를 보냈다고 가정하지 않는다. 실제 대회 제한이 우선이다.

## S1. 최근의 구체적인 문제 사례

```text
말씀하신 업무를 개선할 결과물을 만들기 전에 실제로 해결해야 할 문제부터 이해하고 싶습니다. 현재 담당하시는 업무와 알고 계신 정보를 기준으로 답변해 주세요.

현재 확인 가능한 질문은 한 번에 모아서 드리겠습니다. 확인된 사실과 추정·의견을 구분하고, 모르거나 확인이 필요한 내용은 그대로 말씀해 주세요. 공식 규칙과 실제 관행이 다르면 차이를 알려주세요. 제가 제안하거나 요약한 내용이 현장과 맞지 않으면 이유나 반례를 말씀해 주세요. 근거 자료가 있다면 확인할 수 있는 위치도 부탁드립니다.

먼저, 이 업무에서 최근 일이 잘 안됐거나 불필요한 시간이 많이 들었던 사례 하나를 말씀해 주실 수 있나요?

어떤 일이 들어왔고, 누가 어떤 자료나 도구로 처리하다가 어느 지점에서 문제가 생겼으며, 그 결과 어떤 영향이 있었는지 궁금합니다.
```

## S2. 원하는 변화와 결과의 사용처

```text
방금 말씀하신 [문제 사례]가 개선됐다고 할 때, 누가 어떤 상황에서 결과를 보고 무엇을 다르게 할 수 있어야 하나요?

처음 사용할 수 있는 최소한의 결과 한 가지와, 지금 방식보다 나아졌는지 판단할 수 있는 기준을 알려주세요. 아직 측정하지 않은 수치라면 목표나 추정이라는 점을 구분해 주세요.
```

## S3. 입력 자료·판단 규칙·예외 확인

```text
[판단해야 할 업무 또는 결과]의 기준을 정확히 이해하고 싶습니다.

실제로 사용할 수 있는 입력 예시 하나와, 그 입력에서 어떤 결과가 맞는지 알려주실 수 있나요? 가능하면 비슷해 보여도 다르게 처리해야 하는 예외도 하나 부탁드립니다. 민감정보는 불필요하며 자료 형식이나 항목 예시로 설명해 주셔도 됩니다.

그 판단이 공식 규칙인지 관행인지, 근거를 어디서 확인할 수 있는지도 알려주세요. 값이 없거나 서로 충돌할 때 정해진 처리 방식이 없다면 미정이라고 말씀해 주세요.
```

## S4. 구현 전 최소 범위와 완료 기준 확인

```text
제가 이해한 첫 구현 범위는 다음과 같습니다.
- 해결할 문제와 사용자: [내용]
- 사용할 입력과 만들 결과: [내용]
- 맞아야 하는 대표 사례와 중요한 예외: [내용]
- 이번에는 하지 않을 일: [내용]
- 아직 확인하지 못한 조건: [내용]

이 결과면 실제로 첫 사용을 해볼 수 있을까요? 잘못 이해했거나 꼭 빠지면 안 되는 부분을 짚어주세요. 새 기능을 많이 추가하기보다 이 범위가 업무 목적을 충족하는지와 완료 판단이 맞는지 확인하고 싶습니다.
```

## S5. 애매한 용어·서로 다른 답변 확인

```text
[용어 또는 조건]을 제가 서로 다른 의미로 이해하고 있을 수 있어 확인드립니다.

앞서 말씀하신 내용은 [A]이고, 이번에 말씀하신 내용은 [B]입니다. 적용 대상이나 시점이 달라서 생기는 차이인가요, 아니면 이전 내용을 수정해서 이해해야 하나요?

[구체적인 입력 또는 상황 한 건]에서는 어떤 결과나 다음 행동이 맞는지 알려주시면 그 기준에 맞춰 정리하겠습니다.
```

## S6. 실제 사용·갱신·인계 조건 확인

```text
이 결과를 실제 업무에서 계속 사용하려면 어떻게 갱신하고 전달해야 하는지 확인하고 싶습니다.

이 결과를 어느 시점이나 사건을 계기로 갱신해야 하나요? 아직 정해지지 않았다면 미정이라고 말씀해 주세요.
```

갱신 시점을 확인한 뒤 담당자, 실행 환경, 실패 시 대응이나 최신 결과 구별 방법 중 다음 결정을 바꾸는 사항 하나만 이어서 묻는다.

## S7. 자료 밖의 운영 상황

```text
현재 자료는 [실제로 확인한 기간·집단·채널]을 담고 있습니다. 제공 자료에 잘 드러나지 않지만 실제 운영에서 반복적으로 문제가 생기는 상황 하나를 알려주실 수 있나요?
```

시간대·요일·대상 집단 등의 변화를 확인하는 질문이다. “금요일에 몰리죠?”처럼 이전 대회의 현상을 이번 대회의 사실로 유도하지 않는다. 답변에서 변화가 확인되면 S8 등 현재 답할 수 있는 관련 질문을 모아서 이어간다.

## S8. 변화가 만드는 실제 실패

```text
말씀하신 [담당자가 확인한 상황]에서 기존 방식으로 처리하면 실제로 어떤 문제가 생기나요? 최근 사례 하나를 기준으로 설명해 주세요.
```

문제가 확인되면 현재 대응, 가용 자원, 허용할 수 있는 결과 중 필요한 한 가지를 다음 질문으로 삼는다. “사람이 몰린다”만으로 대기 시간·수요 배수·증원 규모를 정하지 않는다.

## S9. 관측되지 않는 사건

```text
[담당자가 알려준 실패나 예외]는 제공 데이터의 어느 기록에 남나요? 기록되지 않는다면 그 사실을 알려주세요.
```

데이터에 없다는 답변은 발생하지 않았다는 뜻이 아니다. 답변을 받으면 어떤 구현 후보나 검증 한계가 달라지는지 Codex와 함께 명세에 반영한다.
