# 참가자 선택 후의 구현 명세 예

진행자용 합성 사례입니다. [과제 원문](task/README.md), [데이터](task/arrivals.csv), [단계별 답변](FACILITATOR.md)을 연결한 간결한 참고 명세입니다. 실제 구현 완료나 대회 정답을 의미하지 않습니다. 초기 에이전트에게 이 파일을 주지 않습니다.

## 산출물과 범위

- R1: `out/coverage.csv`, 원문이 지정한 열·행 보존·구간별 gap·정렬을 충족한다.
- R2: `out/plan.md`, 관측 사실·한계·담당자 설명·참가자의 대응 선택을 구분한다.
- R3: 실행 코드·검사 방법과 기존 과제 문서의 실행 안내. Python 기본 라이브러리만 사용한다.
- 현재는 명세 확정까지다. 화면, 실시간 알림, 수요 예측, 인력 추천과 실제 배치는 포함하지 않는다.

## 서로 다른 근거

| 종류 | 확인한 내용 | 출처와 한계 |
|---|---|---|
| 원문 요구 | `gap=max(arrivals-capacity,0)`, 관측 행만 출력 | README R1. 계산 방식을 다시 선택할 필요가 없음 |
| 관측 사실 | 8행, 월~목 10시·16시, 접수 82건, 행별 gap 합계 6건 | CSV 전체 및 `python facts.py`. 전체 방문 수요나 접수 포기 건수가 아님 |
| 담당자 설명 | 금요일 14~17시 행사 후 방문 집중·접수 포기; CSV는 완료된 접수만 추출 | 진행자 답변 Q1. 금요일 수요·포기 인원은 미계측이며 CSV에서 확인한 값이 아님 |
| 참가자 선택 | 짧은 주의사항 설명과 담당자 수동 확인; 없는 수치나 자동 대응을 만들지 않음 | 진행자 3단계 선택 Q2. 문구·내부 코드는 이 범위에서 위임 |

## 구현 규칙과 검사

### S1 — R1: 입력 처리와 CSV

- 규칙: 원문 네 열을 읽고 각 행의 gap을 계산한다. 날짜·시간 오름차순, 지정된 다섯 열로 출력하며 없는 구간을 추가하지 않는다.
- 상태: 원문 동작은 `specified`. 참가자 추가 결정으로 누락·잘못된 날짜/수치·중복 구간 입력은 명확한 오류로 중단한다. “누락”만으로 빈 CSV까지 포함시키지 않고, 별도 후속 답변에서 헤더만 있는 CSV의 오류 중단을 확정했다. 날짜·시간·건수 형식과 유효 범위, 오류 문구·내부 코드는 명시적으로 위임한 범위에서 `delegated`다.
- 근거: 현재 표본에는 빈 셀·중복 구간이 없다. 오류 중단 정책은 데이터에서 도출된 사실이 아니라 참가자 선택이다.
- 검사: 정상 8행 보존과 gap `0,0,0,1,0,2,0,3`, 정렬·열 순서, 미관측 날짜/시간 미생성을 확인한다. 제공되지 않은 오류 입력은 별도 검사 사례로 만들며, 성공 산출물로 처리되지 않는지 확인한다. 이전 구간의 여유로 다음 구간 gap을 상계하지 않는다.

### S2 — R2: 보고서에서 놓친 상황 확인

- 후보 A: 본문의 짧은 주의사항 설명. 간결하지만 독자가 확인 항목을 찾아야 한다.
- 후보 B: `확인할 상황 / 근거 유형 / 아직 모르는 사항` 확인표. 대조하기 쉽지만 형식과 분량이 늘어난다.
- 선택: 참가자가 A를 `confirmed`. 담당자가 말한 주의 시간대와 미계측 한계를 설명하고 최신 상황은 담당자가 수동 확인한다. 자동 알림·예측·증원 추천은 제외한다.
- 근거: Q1의 자료 밖 운영 설명 → 확인을 돕는 보고서 후보 → Q2의 참가자 선택. 에이전트가 B를 추천했더라도 A가 현재 규칙이다.
- 검사: 6건은 표본의 구간별 gap으로만 설명한다. 금요일 상황은 담당자 보고로 표시하고 미계측 수요나 포기 인원으로 바꾸지 않는다. 확인하지 않은 수요 배수·인원·임계값이 없어야 한다. R1 CSV에 금요일의 가상 행을 넣지 않는다. 설명 문구는 참가자가 맡긴 범위 안에서 작성한다.

### S3 — R3: 실행과 검사 안내

- 규칙: 실제 코드에 맞는 입력·출력 경로와 실행·검사 명령을 기존 과제 문서에 남긴다. 파일 구성과 동등한 알고리즘은 `delegated`다.
- 근거: README R3. 데이터 통계로 정당화할 필요가 없는 제출 요구다.
- 검사: Python 기본 라이브러리만으로 실행 가능하며 실제 산출물을 다시 읽어 S1을 확인한다. S2의 출처·수치·선택 범위는 별도로 검토한다. 코드와 결과가 아직 없으므로 이 검사가 이미 통과했다고 주장하지 않는다.

## 인터뷰 종료 후 전체 구현 계획

진행자 3단계와 빈 입력 후속 답변까지 받은 경우의 계획이다. 실제 코드·산출물 검증 완료를 의미하지 않는다.

- 목표/범위: 담당자가 관측 구간의 부족량을 정확히 읽고 자료 밖의 주의 상황을 함께 확인한다. R1 coverage.csv, R2 plan.md, R3 코드·검사·실행 안내를 모두 납품하며 자동 알림·수요 예측·증원 추천은 제외한다.
- 전체 흐름: 담당자가 원본 CSV 준비 → S1 검증·계산·정렬 → coverage.csv와 S2 plan.md 생성 → 담당자가 관측값과 제보·한계를 읽고 최신 상황 수동 확인. 확정된 오류 입력은 설명과 함께 중단하고 가짜 정상 결과로 바꾸지 않는다.
- 데이터/구성: 원본 네 열과 관측 행을 보존하고 gap 열을 추가한다. 보고서는 같은 계산 결과와 Q1/Q2의 서로 다른 근거를 사용한다. 필요한 것은 로컬 파일 입출력이며 별도 웹·DB는 요구하지 않는다.
- 구현 순서: S1의 입력→CSV 경로와 손계산 검사 → 같은 결과를 쓰는 S2 보고서 및 출처 검토 → S3 실행 안내와 전체 재현 검사. 선택 기능을 앞에 두지 않는다.
- 수용/준비 여부: S1의 8행·gap 합계 6·정렬·오류 조건, S2의 제보/관측 구분과 미계측 수치 미생성, S3의 실제 명령 재현으로 R1~R3를 확인한다. 후속 빈 입력 결정까지 반영한 이 예시의 필수 계획은 준비됐으며, 실제 금요일 수요량은 미계측 한계로 남는다. 현재 범위는 그 값을 계산하지 않으므로 이를 0으로 채우거나 추가 질문으로 계획을 지연하지 않는다.

## 질문이 명세를 바꾼 순서

1. Q1, 담당자에게 사실 확인: 표본에 드러나지 않은 반복 문제를 중립적으로 질문했다. 답변은 S2의 맥락과 데이터 한계를 바꿨으며 R1 계산 규칙은 유지했다.
2. Q2, 참가자에게 선택 요청: 보고서 설명 방식 A/B의 장단점을 제시했다. A 선택을 S2의 규칙과 검사에 반영했다. 참가자가 함께 정한 오류 정책은 S1에, 문구·코드 위임은 관련 항목에 남겼다.
3. 입력 계약 후속 확인: “누락”이 빈 CSV를 포함하는지 별도로 확인했다. 빈 CSV 오류 중단과 데이터 형식·범위의 한정된 위임을 받은 뒤에야 S1의 해당 규칙을 확정했다.

이 합성 사례의 합의된 명세 범위에 답변 대기 질문은 없다. 실제 수요·포기 인원 등 알려지지 않은 사실은 여전히 미계측이다. 그 값을 알 수 없다는 한계를 유지하는 것과 명세 선택이 미정인 것은 구분한다. 구현은 이후 별도 요청 범위에서 진행한다.
