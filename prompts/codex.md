# Codex용 프롬프트

필요한 블록 하나만 사용한다. C1 이후에는 같은 대화의 맥락을 이어가며, 새 대화에서는 C8을 쓴다. 설치된 fde-kit와 실제 과제·환경의 제약을 적용한다.

## C1. 문제 정의 시작

```text
$fde-kit

지금은 문제 정의 단계다. 내가 업무 담당자와 대화하면서 해결할 문제와 완료 기준을 구체화하도록 도와줘.

과제 또는 최초 요청: [원문]
알려진 시간·환경·제출 조건: [알려진 내용만. 모르면 미확인]

먼저 제공된 자료와 기존 프로젝트 문서를 읽어줘. 이미 확인된 내용을 다시 묻지 말고 사실·가정·미확인을 구분해줘. 아직 구현을 요청하지 않았으므로 질문과 문제 정의에 집중해줘.

필요한 만큼 확인할 것은 여섯 가지야.
- 누가 언제 어떤 판단이나 행동을 위해 결과를 쓰는가?
- 최근 구체적인 사례에서 무엇이 잘못됐고 어떤 영향이 있었는가?
- 원하는 변화와 필요한 산출물, 최소 해결 범위는 무엇인가?
- 어떤 입력과 업무 규칙을 쓰며 누락·충돌·예외는 어떻게 판단하는가?
- 시간·환경·권한·데이터·제출 형식의 제약은 무엇인가?
- 어떤 실제 사례를 통과하면 성공이고 누가 실행·갱신·최신성 확인을 맡는가?

질문 전체를 한꺼번에 나열하지 마. 정확성·범위·검증 가능성에 가장 큰 영향을 주는 질문 하나부터 골라, 담당자에게 그대로 보낼 자연스러운 문장으로 작성해줘. 답이 충분하면 질문을 계속 늘리지 말고 최소 해결 범위와 확인 가능한 완료 조건을 제안해줘. 담당자의 의견, 공식 규칙, 너의 제안을 구분하고 수치·승인·배점을 만들어내지 마.

대회라면 실제 안내와 competition 지침을 먼저 적용해줘. 첫 답변은 현재 이해한 문제와 담당자에게 가장 먼저 보낼 질문 하나만 제시해줘.
```

## C2. 담당자 답변 반영·다음 질문

```text
업무 담당자의 추가 답변이야.
[답변 원문과 관련 질문·자료 위치]

기존 이해와 대조해서 새로 확인된 내용, 바뀐 내용, 아직 애매하거나 충돌하는 내용을 짧게 정리해줘. 상대가 확정하지 않은 규칙·수치·운영 승인을 사실로 바꾸지 마.

질문이 필요하면 해결 방향을 가장 크게 바꿀 다음 질문 하나만 작성해줘. 정보가 충분하면 더 묻지 말고 문제 한 문장, 최소 산출물, 이번에 제외할 범위, 확인할 기대 사례와 남은 가정을 제안해줘.

이미 구현 중이라면 변경이 요구사항인지 단순 설명인지 구분하고 영향받는 코드·자료·검사를 짚어줘. 실제 요구가 바뀌면 BRIEF와 관련 계약을 갱신하고 기존 검증을 다시 사용할 수 있는지 확인해줘. 답변 전달만으로 새 구현 범위가 승인됐다고 가정하지 마.
```

## C3. 범위 확정·구현 또는 분석 실행

```text
$fde-kit
아래 범위로 실행해줘.

목표와 사용자: [누구의 어떤 일을 바꿀지]
입력과 산출물: [자료 위치, 결과 경로·형식]
완료 조건: [확인된 정상 사례와 중요한 예외의 기대 결과]
제약과 제외 범위: [시간·환경·권한·하지 않을 일]

기존 합의와 재사용 가능한 코드를 먼저 확인하고, 가장 작은 동작 경로부터 완성해줘. 내장 도구는 입력·업무 규칙이 맞을 때만 사용해줘. 정확성이나 범위를 바꿀 정보가 없으면 핵심 질문을 하되 그 답과 무관한 작업은 진행해줘.

작은 단일 담당 작업은 짧은 BRIEF와 작업 계약 하나로 관리해줘. 관련 요구 문서·입력·실제 구현 파일·설정·검사·산출물을 빠뜨리지 말고 등록해줘. 이미 승인한 범위에서는 매 단계마다 다시 허락을 묻지 말고 필요한 검증과 사용 안내까지 마쳐줘. 범위 밖 배포·외부 전송·새 에이전트 사용 권한까지 가정하지 마.

첫 실제 검사를 verify --handoff로 기록해줘. 구현·산출물 생성은 검사 전에 끝내고, 진행 메모는 DECISIONS에 둬. 마지막에는 결과 위치, 실제 검사 결과, 남은 한계와 운영 조건을 짧게 알려줘.
```

## C4. 결과 검증·구체적인 약점 확인

```text
$fde-kit
현재 결과가 원래 요구와 완료 조건을 충족하는지 검증해줘.

현재 파일과 기존 검증 근거부터 대조해줘. 이미 유효한 검사를 이유 없이 반복하지 말고, 바뀐 부분이나 아직 확인하지 못한 중요한 위험을 검사해줘. 생성 명령 성공이나 파일 해시만으로 업무 결과가 맞다고 결론 내리지 마.

원래 요구에서 독립적으로 정한 정상·경계·실패 사례를 실제 결과와 비교해줘. 그럴듯한 오답을 통과시킬 위험이 크면 원본을 보존한 복사본에서 중요한 값 하나를 바꿔 검사가 거부하는지도 확인해줘. 체크를 통과시키려고 요구나 기대값을 임의로 바꾸지 마.

보고는 중요한 순서로: 구체적인 약점 위치 → 왜 위험하고 어디까지 영향을 주는지 → 확인 근거 → 필요한 수정 또는 다음 검사. 실제로 발견한 문제만 말하고, 수행하지 않은 검사는 미확인으로 남겨줘. 이번 요청은 검증이며 범위를 늘리는 재설계는 먼저 제안해줘.
```

## C5. 오류 원인 파악·최소 수정

```text
$fde-kit
다음 동작에서 문제가 생겼어.
실행한 작업과 입력: [재현 정보]
기대 결과: [원래 요구]
실제 결과 또는 오류: [관찰 내용·로그 위치]

가장 작은 재현 사례로 원인을 좁히고 요청 범위 안에서 수정해줘. 원인 가설과 근거를 구분하고, 새 증거 없이 같은 명령이나 추측성 수정을 반복하지 마. 관련 없는 구조 변경은 하지 마.

수정 후 원래 실패 사례와 영향받는 중요한 동작을 실제로 검사해줘. 실패 로그를 지우거나 이전 성공 기록으로 대체하지 말고, 현재 코드·입력에 대한 검증과 handoff를 갱신해줘. 마지막에는 원인, 바꾼 부분, 확인 결과와 남은 불확실성만 짧게 정리해줘.
```

## C6. 시간이 부족할 때 범위 조정

```text
$fde-kit
남은 시간은 [시간]이고 제출 조건은 [조건]이야.

현재 구현과 검증 상태를 기준으로 필수 완료 조건, 아직 위험한 부분, 미뤄도 되는 기능을 구분해줘. 구현됐다는 이유만으로 검증까지 끝났다고 보지 마. 알 수 없는 작업 시간을 확정값처럼 말하지 마.

필수 결과와 마지막 검증·제출 시간을 지킬 수 있는 최소 범위 하나를 추천하고, 무엇을 포기하며 어떤 영향이 있는지 설명해줘. 실제 안내에 없는 배점으로 우선순위를 만들지 마. 이 요청에서는 조정안만 제시하고, 범위 변경은 내가 선택한 뒤 적용해줘.
```

## C7. 세션 종료·인계

```text
$fde-kit
여기까지 작업을 정리해서 다음 세션이 이어갈 수 있게 해줘. 새 기능은 만들지 마.

현재 파일과 실제 검증 상태를 확인하고, 목표·합의한 범위·산출물 위치·검사 근거·남은 문제·다음 행동 하나를 기존 기록에 남겨줘. 요구가 바뀌지 않았다면 진행 보고 때문에 BRIEF를 다시 쓰지 말고 DECISIONS를 사용해줘. 중복 요약 문서를 추가하지 마.

반복 사용할 결과라면 누가 어느 환경에서 언제 원본을 수정하고 생성·전달하는지, 최신 결과를 어떻게 구별하는지도 짧게 남겨줘. 확인되지 않은 운영 책임이나 권한은 미확인으로 표시해줘. 현재 상태에 맞는 handoff를 생성하고 다음 세션에서 처음 읽을 위치를 알려줘.
```

## C8. 새 세션에서 재개

```text
$fde-kit
이 프로젝트를 이어가줘. 현재 요청 또는 이전 합의에서 달라진 내용은 [없음 / 변경 내용]이야.

AGENTS.md와 실제 과제, BRIEF·DECISIONS를 읽고 status를 실행한 뒤 HANDOFF를 대조해줘. 이전 세션의 완료 주장이나 저장된 상태만 믿지 말고 현재 입력·코드·검사·결과의 근거가 유효한지 확인해줘. 추가되거나 등록에서 빠진 관련 파일도 살펴봐줘. 대회라면 현재 안내와 competition 제약을 적용해줘.

현재 목표, 실제 검증된 범위, 남은 핵심 문제와 다음 행동 하나를 짧게 설명한 뒤 이미 승인된 남은 작업을 진행해줘. 범위나 권한이 불명확한 부분만 질문하고, 불필요한 재설치·전체 재작성·성공 검사 반복은 하지 마.
```

## C9. AI 사용 허용 단계의 설명 연습

```text
$fde-kit
AI 사용이 허용된 준비·작업 단계에서 내가 결과를 이해했는지 연습하고 싶어. 실제 AI 금지 후속 서술형이라면 답안 작성·첨삭·문제 풀이를 하지 마.

현재 결과를 근거로 내가 설명해야 할 중요한 질문을 하나씩 해줘. 입력이 결과로 바뀌는 흐름, 중요한 설계 선택과 대안, 실제 검사 범위, 구체적인 약점과 영향, 다음 개선 중 필요한 것을 골라줘.

먼저 모범 답안을 주지 말고 내 답을 기다려줘. 답을 받으면 코드·문서·검사 결과와 다른 부분을 짚고 필요한 만큼만 설명해줘. 숨은 채점 기준·예상 점수·존재하지 않는 약점을 만들어내지 마.
```
