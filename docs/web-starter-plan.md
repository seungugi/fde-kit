# Web starter and meal simulation implementation plan

Goal: add an opt-in reusable FastAPI/Jinja2/HTMX/SQLite/pytest skeleton to FDE Kit, exercise it with a working Korean monthly-meal app, publish the kit update and show the local app.

User approved the recommended stack and implementation, then explicitly delegated all remaining simulation choices. No additional product approval gate is pending. Existing applications retain their stack. This is a local synthetic standard-profile exercise, not the official competition environment.

## Contract and decisions

- Generic starter is under skills/fde-kit/assets/web/starter. Optional meal overlay is under skills/fde-kit/assets/web/examples/meal-planner. web.py init NEW_PATH [--example meal-planner] copies the starter then the overlay without modifying an existing target. It does not download dependencies or launch a server. Generic app is a small persistent item board proving create/list/delete. Meal example is opt-in.
- Shared starter files: app/main.py application factory `create_app(db_path=None, demo_mode=None)`, app/db.py, app/security.py, app/features.py router/hooks, app/__init__.py, templates/base.html + index.html + error.html, static/app.css + app.js + vendored htmx.min.js, tests, requirements.txt, README.md. Meal overlay replaces features.py and templates and adds app/planner.py, synthetic data and tests. The UI owner writes templates/CSS/JS only; backend owner writes app/data/tests only. Parent owns kit integration, requirements, documentation, scaffolder, vendor asset and release.
- Runtime: uvicorn app.main:app --host 127.0.0.1 --port 8765. Explicit DEMO_MODE=1 enables synthetic user switching; outside demo mode protected mutations remain unavailable until a real identity adapter is integrated. APP_DB controls durable SQLite location; default project data/app.sqlite3, ignored by git. Session secret is environment-supplied or process-random for local demonstration. Server-side role checks and CSRF required for mutations. No real SSO/authentication claim.
- Shared functions are agreed directly by backend owner; app/main.py provides Jinja templates, session setup, database path, /health, static files, and installs app.features.router. Feature module initializes schema/seed through `initialize(db_path)` and owns its rendering helpers. Context names below are the interface with templates.
- Simulated task: 120 fictional members; November 2026 weekdays (21 lunches); one menu set/day; each meal <=8000 KRW. Interest means a unique member-menu preference with cancellation, never a reservation or measured attendance. Administrator creates draft, edits with validation, publishes; published plans must be reopened before editing. Two synthetic planning constraints: menu at most twice/month and at least 5 serving-day indices apart. Fridays cannot use fryer equipment (simulated stakeholder constraint, explicitly disclosed in demo; no claim of blind discovery). All numbers and policies are exercise assumptions.
- Deterministic feasible greedy planner prioritizes declared interest, uses stable ties, obeys every hard constraint, and compares with a simple rotation baseline. It must report heuristic/feasible, never prove an optimum from a valid result. Seed enough affordable non-fried menus for all dates. Actual attendee count and nutritional adequacy are not inferred.
- Data/UI: menu fields id, name, category, price, description, components (list), requires_fryer, interest_count, interested. user fields id/name/role (member or admin). Common template context request/csrf/demo_mode/user/page/month/message/error. Calendar context weeks (7 day cells each: date/day/in_month/is_workday/menu), plan (status/version/month), stats (days/filled/total_cost/average_cost/interest_score), issues list, menus. Menu listing supplies q/category/sort/menus. Insights supplies ranked menus and computed totals. Backend communicates additional exact fields to UI owner before integration.
- Routes: GET / (month query); /menus (q/category); /insights; /about; /health; /export.csv?month=. POST /demo/switch (role, csrf); /interests/{menu_id} (intent add/remove, csrf); /plans/generate (month/version/csrf); /plans/publish and /plans/reopen (month/version/csrf); /plans/{date}/replace (menu_id/month/version/csrf). All mutating values validated server-side. Stale plan version returns conflict without writing.
- HTML forms work without HTMX. Interest updates use HTMX targeting a menu-card partial; error responses retarget a visible notice. Other edits may use normal POST/redirect. Local assets only; no runtime CDN or external API dependency.
- Visual direction: polished Korean workplace service '온담 / ONDAM', warm ivory background, deep evergreen sidebar, burnt-orange accent, restrained serif-like heading/system Korean sans text, generous spacing, responsive monthly calendar, menu library with clear tags, interest rankings, a concise explain-this-build page. No food-image dependency or emoji-heavy placeholders. Label synthetic/demo context unobtrusively but clearly.

## Tasks and review focus

- [x] T1 Skeleton/scaffolder: failing tests for generated app import, no-overwrite, full/core asset handling, default local assets; implement and run. Keep existing CLI semantics and optional assets opt-in.
- [x] T2 Meal behavior: first failing tests for unique/idempotent interest and cancellation, member/admin separation, CSRF, budget/Fri-fryer/repeat/gap constraints, optimistic conflict, published locking, state after recreation, export accounting; implement and verify from original stored records.
- [x] T3 UI: render all screens, empty/errors/loading, mobile layout, keyboard/form labels; connect all controls to real routes. Template inputs must match this contract; clarify with backend owner as needed without new user questions.
- [ ] T4 Integrate: initialize with new Kit, register actual test command and tracked files, run API lifecycle simulation and fresh independent review, visually inspect served app, correct important failures, preserve truthful verification and explanation scope. Publish kit update using expected-head protection and verify uploaded bytes.

Review focus: unauthenticated/forged role mutations; double click and concurrent edits; failed generation destroying an existing plan; published/draft visibility; schema-correct but policy-invalid output; rendering and input escaping; newly scaffolded project on another directory; no web dependency forced on ordinary kit installation.

Actual evidence and release outcome will be recorded here after execution; never label command success as human review or complete UI verification.

Release candidate checked: 94 kit tests passed / 2 host skips, 4 generated generic tests passed, 20 generated meal tests passed, real browser flow and responsive layout inspected.
